GitHub Copilot 记忆功能落地方案

公司电脑版 · VS Code Copilot 插件 · 无 CLI · 无云端 Memory

约束条件：公司电脑使用；只有 VS Code 的 GitHub Copilot 插件；没有 Copilot CLI；企业策略禁用云端 Copilot Memory。
安装方式：推荐用户级安装（python install_user.py）——装在用户主目录，装一次所有仓库都能用，记忆按仓库自动分区。

一、结论：能力边界

能力能否使用说明
VS Code 内置 Memory Tool可以数据只写本机 workspaceStorage，不经过 GitHub 云端
MCP server（自建本地记忆）可以VS Code 是完整 MCP 客户端，本地 stdio 进程即可
指令文件（AGENTS.md 等）可以纯本地文件，永远可用
Copilot Memory（云端）不可以需账号侧开启，企业策略常禁用
Copilot CLI不可以未安装或不允许
关键认知
WorkBuddy 的「记忆」本质是仓库里可版本化的 Markdown 文件。要在 Copilot 侧做到同构，重点不是找一个「云端记忆」开关，而是让 Copilot 的记忆落到真实文件里——这样它能进 git、能跨机器同步、能被其他 agent 读到。

二、三层等价结构

第 1 层 · 指令层
AGENTS.md / .github/copilot-instructions.md — 稳定规则，常驻注入上下文
第 2 层 · 记忆层
.copilot/memory/*.md（经 MCP 读写）— 运行时积累，进 git，可跨 agent
第 3 层 · 会话层
Copilot 内置 Memory Tool 的 session scope — 单次对话的临时笔记

三、方案 A：只用内置 Memory Tool（零配置）

3.1 确认设置

Ctrl+Shift+P → Preferences: Open User Settings (JSON)：

{
  "github.copilot.chat.tools.memory.enabled": true
}

这个开关默认就是开的，且是纯本地功能，不依赖 Copilot Memory。

3.2 三档 scope

scope路径跨会话跨项目适合装
User/memories/是是（前 200 行自动注入）个人偏好、常用命令
Repository/memories/repo/是否仓库约定、构建命令
Session/memories/session/否否当前任务临时笔记

在 Chat 里直接说「记住：…」即可，模型会自己判断落到哪一档。管理命令：Chat: Show Memory Files / Chat: Clear All Memory Files。

致命限制 — 这才是需要上 MCP 的原因
这些文件落在 VS Code 的 workspaceStorage 里，不在你的仓库里：公司电脑 ↔ 家里电脑不同步；不进 git，同事看不到；换 profile 或重装扩展可能丢；Claude Code / Codex / WorkBuddy 完全读不到。

四、方案 B：本地 MCP 记忆层（推荐）

本方案提供的记忆 MCP server 零依赖——只用 Python 标准库，不联网、不需要 API key，把记忆存成仓库里的 Markdown。

两种装法，先选一个
用户级（python install_user.py）装在用户主目录，装一次，所有仓库都能用，记忆按仓库自动分区——公司电脑推荐这个。 仓库级（./install.sh）装在每个仓库里，记忆跟着仓库进 git、能共享给同事。

4.1 用户级安装（装一次，全机共享）

1
执行安装Windows 用 Git Bash 或 PowerShell 都行，py install_user.py 也可以。纯标准库，无需 pip install。先用 --dry-run 看它要干什么而不实际写盘。
2
重启 VS Code，打开任意仓库然后 Ctrl+Shift+P → MCP: List Servers → 启动 memory。
3
验证Chat 里问「调用 memory_write 记住：这个项目用 pnpm 不是 npm」，再问「调用 memory_list 看看记住了什么」。切到另一个仓库再问，应该看不到刚才那条，但能看到 global 里的。
4
卸载python install_user.py --uninstall，只移除装的东西，你原有的配置和偏好完整保留。

用户级装在哪

~/.copilot/memory-kit/memory_server.py — server 本体
~/.copilot/memory/ — 共享记忆存储（global/ + projects/）
~/.copilot/instructions/memory.instructions.md — 用户级定向指令
~/.copilot/copilot-instructions.md — 用户级常驻指令（追加，不覆盖原内容）
%APPDATA%\Code\User\mcp.json — VS Code 用户级 MCP 配置
~/.copilot/mcp-config.json — 便携式 MCP 配置（Copilot harness 直接读）

记忆怎么分区

~/.copilot/memory/global/ — 跨项目通用规则（提交规范、个人偏好）
~/.copilot/memory/projects/my-backend-a1b2c3/ — 只属于这个仓库的记忆
~/.copilot/memory/projects/my-frontend-d4e5f6/ — 另一个仓库，互不可见

项目身份来自 server 启动时的工作目录——VS Code 启动 stdio server 时工作目录就是当前打开的仓库。server 会向上找最近的 .git 目录确定项目根，所以 monorepo 子目录也算同一个项目；目录名后缀是路径短哈希，防止同名仓库撞车。想手动指定就设 MEMORY_PROJECT。

scope写到哪检索时看到
project（默认）当前仓库的分区本项目 + global
globalglobal/只看 global
all—所有项目的分区 + global
唯一需要你注意的
跨项目通用的规则才写 global。把项目专属决策放进 global 会污染其他仓库——这是这套设计里唯一会「串味」的地方。

记忆怎么组织：按日期 + 长期沉淀

每个分区内部按日期分文件，和 WorkBuddy 的记忆结构一致：

projects/my-backend-a1b2c3/MEMORY.md — 长期沉淀：跨天仍成立的规则
projects/my-backend-a1b2c3/2026-10-22.md — 当天的日志

一个文件里放多条记忆，每条以二级标题开头：

## 数据库迁移必须先写回滚脚本

<!-- tags: db, migration -->
<!-- updated: 2026-10-22T12:00:00+08:00 -->

迁移脚本要配套回滚脚本，否则线上出问题无法快速恢复。
操作落在哪
memory_write（默认）追加到当天的日志文件
memory_write + bucket: "curated"写进 MEMORY.md
memory_write（同标题已存在）原位更新那条，不新增

日常琐事、临时决策 → 日志文件；反复出现、跨天仍成立的规则（提交规范、架构约定、用户明确表达的偏好）→ MEMORY.md。

正文里可以自由用 # 和 ### 标题，但 ## 会开启新条目——代码块（```）里的 ## 不会被误解析。

旧 store 怎么办
「一记忆一文件」的旧格式两种模式都能读，不需要转换：换了组织方式只影响新写入落在哪，旧文件照旧可检索。

4.2 仓库级安装（记忆跟着仓库走）

1
安装到目标仓库./install.sh /path/to/your-repo，脚本幂等，不删除任何已有文件；--force 才覆盖。
2
启动 MCP serverVS Code 里 Ctrl+Shift+P → MCP: List Servers → 找到 memory → start。或直接开 Agent 会话，工具自动出现。
3
验证Chat 里问「调用 memory_write 记住：数据库迁移必须先写回滚脚本」，然后「调用 memory_list 看看记住了什么」。仓库里应出现 .copilot/memory/ 下的新文件。
4
纳入 gitgit add .copilot AGENTS.md .github .vscode mcp。若不想提交记忆本体，在 .gitignore 里加 .copilot/memory/*.md 并保留 MEMORY.md 索引。

安装后的仓库结构

AGENTS.md — 跨工具规则，Copilot / Claude / Codex 都读
.github/copilot-instructions.md — Copilot 专属、常驻注入的记忆协议
.github/instructions/memory.instructions.md — 按 applyTo glob 定向
.vscode/mcp.json — MCP 客户端配置（顶层 servers 键）
mcp/memory_server.py — 零依赖记忆 server
.copilot/memory/MEMORY.md — 长期沉淀的记忆
.copilot/memory/2026-10-22.md — 当天的日志（按日期自动命名）

MCP 暴露的工具

工具作用
memory_search(query, limit, scope, since, until)BM25 排序（带长度归一化与词频饱和）+ 短语加成；标题词 3×、标签 2×、正文 1×；英文做词形折叠（score / scored / scoring 同词），中文只在连续汉字串内切二元组、不跨空格标点；重复内容合并、低于最高分 40% 的结果丢弃；可按日期区间过滤
memory_write(title, content, tags, scope, bucket)写入或更新一条记忆，同标题自动原位更新；bucket 选 daily（默认）或 curated
memory_read(name, scope)读全文；name 传日期（2026-10-22）可读出那天的全部记忆
memory_list(scope, date, bucket)列出全部，带预览；可按日期或 bucket 过滤
memory_delete(name)删除，仅在明确要求时使用
装了 MCP 不等于 Copilot 会主动调用
必须靠指令层驱动。.github/copilot-instructions.md（或用户级的 ~/.copilot/copilot-instructions.md）写明了：开工前先 memory_search；命中结果优先于默认做法（那是这个项目真正做过的决定）；用户表态、决策消歧、发现非显然事实就 memory_write；记忆过时则改，不要新增一条矛盾的。

五、指令层分工

文件读它的东西放什么同步方式
AGENTS.md所有主流 agent（Copilot / Claude Code / Codex / opencode / pi）跨工具通用：构建命令、目录约定、提交规范走 git
.github/copilot-instructions.md仅 CopilotCopilot 专属行为、记忆协议走 git
.github/instructions/*.instructions.md仅 Copilot，按 applyTo glob 触发特定语言或目录的规则走 git
~/.copilot/copilot-instructions.md仅 Copilot，跨项目个人全局偏好不同步（~/.copilot/instructions 不走 Settings Sync）
冲突不会被规则解决
GitHub 现在多个自定义指令文件是合并的，不再按优先级回退。别在两个文件里写互相矛盾的内容——冲突不会让某个文件胜出，只会让模型困惑。

六、公司电脑特有注意事项

  1. 不能装东西 — 本方案只依赖系统自带 python3，无需 pip install。Windows 上 install_user.py 会自动找 python.exe 或 py 启动器下的解释器，找不到就用 --python 手动指定；macOS/Linux 上 /usr/bin/python3 即可。
  2. 不能联网 — 记忆 server 完全离线；memory_search 是本地 BM25 检索，不调用 embedding API。
  3. MCP 审批 — 首次调用工具会弹权限确认，选「Always allow」避免每次都点。
  4. 企业策略可能禁用 MCP — 若 MCP: List Servers 看不到 server，退回纯文件方案：让 Copilot 直接用内置 read_file / edit_file 读写 ~/.copilot/memory/ 下的 Markdown，指令文件里已写了这条降级路径。
  5. 仓库不能提交 — 把 MEMORY_ROOT 指到仓库外，例如 ~/copilot-memories/<repo-name>，改 MCP 配置的 env 即可。
  6. 多仓库共用一份记忆 — 用用户级安装，它自动按仓库分区，既共享又不会串味。
  7. 不想留痕于用户目录 — 用户级安装只写 ~/.copilot/ 和 VS Code 用户配置目录，不碰任何仓库目录，卸载用 python install_user.py --uninstall。

七、验证状态

本机已实测通过：协议握手 initialize、tools/list、写入、检索（含中文查询「commit 规范怎么写」正确命中）、读取、缺失记忆报错、MEMORY_ROOT 路径解析、安装脚本幂等性。

用户级安装额外实测通过：仓库分区隔离（A 仓库看不到 B 仓库的记忆）、已有用户配置的合并保留（mcp.json 里带注释的 JSONC、其他 server 条目、你写的个人偏好全部原样保留）、卸载精确还原、JSONC 解析、Windows 路径解析。

按日期组织的布局实测通过：同日多条写入同一文件、同标题原位更新不产生重复、删除单条不影响同文件其他条目、按日期读取、curated 与 daily 分桶、旧格式 store 的读取、代码块内的 ## 不被误解析、多进程并发写入不丢条目。

回归测试固定在 tests/test_smoke.py（19 个用例，仅标准库）：python3 tests/test_smoke.py。
